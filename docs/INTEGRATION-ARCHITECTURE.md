# Integration architecture / بنية الدمج

## Current integration boundary

The repository currently contains:
- A normalized catalog of HushGram's 194 Instagram manifest entries.
- A separate candidate inventory of 105 Piko, Brosssh and Oxbow manifest entries.
- Pinned source commits and preserved HushGram LICENSE/NOTICE.
- Catalog validation CI.

It does **not** yet contain the upstream Kotlin patch implementation or Java extension implementation. The metadata catalog is not itself an MPP package.

## Reproducible baseline build

`.github/workflows/upstream-baseline-build.yml` checks out HushGram at immutable commit
`da56d39d7c001bf052bcb7951e3051224bd39928` and invokes the upstream Gradle task
`:patches:buildAndroid`. The workflow uploads the upstream baseline MPP,
CycloneDX SBOM and SHA-256 checksum as a workflow artifact.

This is a **baseline build**, not the merged Instagram Ultimate Patches bundle. It exists to:
1. Prove that the pinned source revision can be built reproducibly in CI.
2. Preserve an inspectable MPP artifact and SBOM for the baseline.
3. Establish a known-good comparison point before importing or porting candidate patches.

The baseline artifact must not be renamed or published as an IUP release.

## Important distinction

A successful catalog validator only checks the JSON inventory. A successful baseline build proves the pinned HushGram project builds. Neither proves that any extra candidate patch has been ported or that a combined IUP package exists.

## Canonical implementation architecture decision (2026-11-21)

IUP will follow HushGram's actual Gradle project structure rather than inventing a parallel patch framework. The HushGram source layout is the reference implementation for the MPP format and runtime integration:

- `patches-list.json` is generated by `:patches:generatePatchesList`; it is not maintained as a hand-authored substitute for source.
- `patches/src/main/kotlin/app/morphe/patches/instagram/` contains executable patch classes, fingerprints, bytecode edits and patch dependencies.
- `extensions/instagram/` contains Java code injected into Instagram and the feature-specific runtime APIs.
- `extensions/shared/library/` supplies shared preference storage, settings UI, localization, diagnostics and common extension facilities.
- `patches/src/test/kotlin/` and extension test source sets hold source/DEX/behavior tests.
- `patches/build.gradle.kts`, root Gradle configuration, version catalog, resources, manifest and generated catalogs are part of the build contract.
- `NOTICE`, `provenance.json`, `sources/instagram-sources.json`, per-file headers and upstream licenses preserve third-party attribution.

### Repository layout to converge on

IUP's final source tree will mirror the HushGram Gradle layout so upstream patches can be integrated with minimal structural translation:

```text
IUP/
  patches/                         # Kotlin patch implementations and tests
  extensions/
    instagram/                    # Instagram runtime Java + resources
    shared/library/               # settings, persistence, localization, diagnostics
  scripts/                        # catalog generation, localization, verification
  sources/instagram-sources.json  # pinned source/license/provenance ledger
  provenance.json
  NOTICE
  patches-list.json                # generated; never hand-edited
  patches-bundle.json              # Morphe source index
  fixtures/                        # ignored local APK/APKS test inputs
```

### Import strategy

1. Treat the pinned HushGram source as the canonical base, including its Gradle wrapper, build logic, extensions, resources, tests and generated-source tasks. Do not replace it with a JSON-only catalog or a thin workflow that merely builds a separate checkout.
2. Preserve HushGram's original files and license notices. Track imported files by upstream commit and path in provenance metadata.
3. Port extra-source features into the matching HushGram packages and extension APIs. Do not import a source's unrelated settings framework when HushGram already provides the equivalent runtime.
4. Generate `patches-list.json` from the actual patch source after each port; run the upstream test/build tasks from the IUP working tree.
5. Keep source-level compilation and unit tests independent from exact APK verification. A local APK fixture is not required to establish the project layout, compile the extension, run fixture-free tests or create the baseline MPP.

### APK requirement clarified

An Instagram 456 APK is **not required** to inspect or reproduce HushGram's architecture, import its source tree, port Java/Kotlin code, wire settings/resources, generate the catalog, compile, run tests that do not need real DEX fixtures, or build a baseline MPP. The exact target APK (or equivalent trusted DEX/MobileConfig fixture) is only required for evidence that a specific fingerprint/flag actually matches 456 and for patch-application/runtime verification. These are separate gates; absence of the APK must not block structural integration work.

### Current boundary

The current IUP repository is still metadata/docs-only (27 tracked paths at this decision point). The existing `Pinned HushGram baseline MPP build` checks out HushGram into a separate workflow directory and builds it there; it does not yet make IUP itself a HushGram-shaped source project. The next implementation milestone is to bring the complete pinned HushGram project into IUP's source tree, then apply source ports there.
